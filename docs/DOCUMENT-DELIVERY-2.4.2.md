# Document delivery and reference scope — runtime 2.4.2

This document describes the runtime 2.4.2 source package at packaging time. The separate [October 12 production audit](PRODUCT-RELEASE-20261012.md) records subsequent candidate/native and deployed acceptance with their limits. The web retains the original Aug5 interface, real multi workflow and thin compatibility patch. The document-delivery patch does not replace the frontend, worker, model choice or resource budget.

The hosted server tells the scientific roles when a source-anchored document postprocessor is available. Planning, implementation and review assess the original statistical claims and the correction justified by executed evidence. They do not attempt an uncaptured DOCX write in R or claim that a later revision file already exists. The standalone CLI and native skill do not receive this hosted capability by default.

After numerical scientific acceptance, the bounded editorial postprocessor creates any proposed DOCX revisions and records the actual source SHA, application/model receipts, artifact SHA and delivery status. Deterministic reports are compiled afterward so that their delivery section describes the actual outcome. Earlier analyst prose remains phase-labelled rather than being rewritten into a claim that a file existed at that stage. Original source documents remain unchanged; proposals are neither numerical ground truth nor proof that the whole document is correct.

`scientificSuccess` and `scientificStatus` describe numerical acceptance. `productSuccess` and `productStatus` also require delivery of an explicitly requested document proposal. A missing, omitted, failed or mismatched required DOCX proposal keeps full delivery partial and prevents the completed-product celebration while preserving accepted numerical findings. The request-target heuristic matches required uploaded DOCX names and source hashes; an optional contextual PDF that produces no revision does not by itself invalidate a delivered required Word proposal. Conditional no-proposal outcomes remain unresolved rather than being certified as no edit needed.

The narrow pooled-t reference guard distinguishes explicitly labelled source/comparison/observed diagnostic quantities from the selected design. Those diagnostics remain recorded and are not certified by the primary reference. Primary selected counts, achieved power and preceding-design power still receive their applicable checks. The formulas and numerical tolerance are unchanged. This semantic boundary correction has component tests; it is not a new accuracy cohort or a retroactive rescore of earlier trials.

Prior 2.4.1 evidence includes separately scoped scientific checks, an actual fresh RDS follow-up with live/history file-byte downloads, and a minimal source-anchored DOCX proposal with prose qualifications. Earlier ZIP/download/history defects and a later incomplete document-delivery trial remain retained. Their successes and failures do not validate 2.4.2. The rejected rewritten frontend, all previous packages, immutable scored studies and native skill 2.3.1 evidence remain separate and unchanged.

Shared preliminary interpretation can contain approximate answer suggestions visible to the reviewer. The workflow remains candidate-blind after shared preprocessing, not fully answer-blind or independent of common model errors. Source tests, successful execution and review do not establish broad scientific accuracy, universal multi superiority or native/API equivalence.

The optional portable runner contains the eight-file Node core and requires installed R/jsonlite, with no cloud database or npm runtime dependency. Hosted PDF/XLSX/DOCX parsing, editorial postprocessing and report compilation use the separately pinned optional integration dependencies. Native instructions/checkers remain 2.3.1; their historical model/version wording is not the current runner pin. Runtime manifests record exact source hashes. Candidate/native and production receipts must be checked separately before making a deployed-product claim.
